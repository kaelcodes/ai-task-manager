## Scope

## Build & output

**Prerequisites**
- Node (via the project's Author Software NVM) + npm, both working.

**Command**
```
npm run tauri build
```

This runs `beforeBuildCommand` (`npm run build` = `tsc && vite build`), compiles the Rust release binary, and produces the NSIS installer.

**Output**

## Configuration notes

- **Version** is set in two places and must stay in sync: `package.json` and `src-tauri/tauri.conf.json` (both `0.2.0`). NSIS uses the `tauri.conf.json` version for upgrade detection.
- **Static VC runtime / `STATIC_VCRUNTIME` warning:** The build prints a non-fatal `STATIC_VCRUNTIME is deprecated; use build.windows.staticVCRuntime` warning. The `build.windows.staticVCRuntime` config key only exists in `@tauri-apps/cli >= 2.12.0`; this project is on **CLI 2.11.4**, whose config schema rejects that key (`Additional properties are not allowed ('windows' was unexpected)`). Fixing the warning therefore requires a CLI upgrade, which is **out of scope** for this minimal module. The warning is cosmetic and does not affect the produced installer. **Deferred** until a deliberate Tauri CLI upgrade.

## WebView2 requirement

The app renders through Microsoft Edge WebView2. It is present by default on current Windows 11 and most updated Windows 10 machines. On a machine without it, the WebView2 runtime must be installed (Microsoft Evergreen runtime). State this in release notes.

## Unsigned installer / SmartScreen caveat

The installer is **not code-signed**. On first run, Windows SmartScreen may warn ("Windows protected your PC"); the user clicks **More info → Run anyway**. Code signing is deferred (requires a paid certificate). Note this in any distribution.

## Data locations (why upgrades preserve data)

- **Tasks & preferences:** SQLite `tasks.db` in the app data directory (outside the install folder).
- **API key:** Windows Credential Manager (service `ai-task-manager`, user `openai-api-key`).

Because both live outside the install directory, an NSIS upgrade over a previous version does not remove them.

## Migration-checksum safeguard (critical for upgrades)

`tauri-plugin-sql` (sqlx) checksums each migration's **SQL text, including whitespace**. If migration 1's SQL differs by even indentation between a released version and an upgrade, the app fails with `migration 1 ... has been modified` and the existing database will not load. **Do not edit existing migration SQL (text or indentation) between releases.** New schema changes must be added only as new, higher-version migrations. (This exact break occurred and was fixed during Module 7.)

## Upgrade test procedure (manual — PASSED, highest priority)

1. Install an older version (e.g. `0.1.0`), create a task, set a preference, and save an API key.
2. Install `0.2.0` over it (run the new installer without uninstalling).
3. Confirm **tasks, preferences, and API-key status are all preserved**, the app launches, and there is **no** `migration ... has been modified` error.

Result: user confirmed the upgrade preserved existing data — tasks, preferences, and API-key status remained intact, with no migration-checksum error.
